## 1. Conventions

### 1.1 Base path, versioning, format
- All routes are under `/api/v1`. Paths in the tables below are **relative to `/api/v1`**.
- A breaking change (removed field, changed type/meaning, new required field, changed status code semantics) requires `/api/v2`; additive changes (new optional request fields, new response fields, new endpoints, new enum values documented as extensible) stay in v1. Clients must ignore unknown response fields.
- JSON only (`application/json; charset=utf-8`), except `POST /sources/upload` (`multipart/form-data`). Field names `snake_case`; path segments `kebab-case`; enum values `UPPER_SNAKE` (GLOSSARY §3).
- IDs are UUIDv7 strings. Timestamps are RFC 3339 **UTC** (`...Z`) in both directions; a request timestamp with a non-UTC offset is accepted and normalized to UTC. Time-zone–aware views (calendar) take an explicit IANA `tz` query param.
- Money: decimal string (`"12.50"`) + ISO 4217 `currency`; never float.
- OpenAPI 3.1 is **auto-generated by FastAPI** from the Pydantic schemas named here, served at `GET /api/v1/openapi.json` (docs UI at `/api/v1/docs`). In `ENV=production` both are disabled unless `OMNIGROWTH_EXPOSE_OPENAPI=true` (see §9 Q9). A CI check diffs the generated `openapi.json` against a committed snapshot so contract changes are explicit.

### 1.2 Authentication and authorization (ADR-0006)
- `Authorization: Bearer <token>` on every route **except** `GET /health` and `POST /auth/login`. Inbound webhooks (`/webhooks/inbound/*`) authenticate with HMAC instead (§6.6), never bearer tokens.
- Token: opaque, 256-bit random, prefix `og_` for secret-scanner detection; stored as `sha256(token)` in `api_tokens` (high-entropy token → fast hash is correct; argon2id is used for **passwords** only). Session tokens expire (default 12 h, config `OMNIGROWTH_TOKEN_TTL`); personal access tokens (`POST /auth/tokens`) have an explicit `expires_at` (max 90 days). Revocation is immediate (row lookup on every request).
- Roles (`UserRole`): `VIEWER` < `EDITOR` < `OWNER`; "Min role" in tables is inclusive upward. Single tenant: every user sees every brand (per-brand scoping is §9 Q2).
  - `VIEWER`: all reads except secrets, raw model payloads, global audit.
  - `EDITOR`: create/edit brands' content objects, sources, campaigns, approvals (§37 actions), analytics ingest, experiments.
  - `OWNER`: users, brands create/archive, campaign archive (C12), platform accounts + credentials, live-enable, settings, routing profile/overrides, webhook endpoints, global audit, `MANUAL_CONFIRM_NOT_PUBLISHED` reconciliation (J13), `mark-deleted` (P9).
- Missing/invalid/expired token → `401 UNAUTHORIZED` with `WWW-Authenticate: Bearer`. Valid token, insufficient role → `403 FORBIDDEN`.
- **CSRF: not applicable.** The API never sets or reads cookies; credentials travel only in the `Authorization` header, which browsers never attach automatically to cross-site requests, so a third-party page cannot ride an authenticated session. CORS is an explicit origin allowlist (`OMNIGROWTH_CORS_ORIGINS`, default empty; the Phase 11 Vite origin is added then) with `allow_credentials=false`. **Invariant:** if cookie auth is ever introduced, CSRF protection becomes mandatory in the same change (a test asserts no `Set-Cookie` header is ever emitted by `/api/v1`).
- First OWNER is created by a CLI command (`uv run poe create-owner`), not by an unauthenticated API route. There is no self-signup.

### 1.3 Pagination — `Page[T]`
- All list endpoints return `Page[<Entity>Read] { items: list[T], next_cursor: str | null }`. `next_cursor = null` ⇒ last page. No total counts (expensive, unstable under concurrent writes); a dedicated `/…/count` can be added later if a view needs it.
- Query: `limit` (default 50, min 1, max 200), `cursor` (opaque, from previous `next_cursor`).
- Default order `id DESC` (UUIDv7 ⇒ newest first). Endpoints that allow `sort` accept only an explicit allowlist per endpoint (e.g. `scheduled_at`, `created_at`); cursor encodes `(sort_value, id)` as base64url JSON. A cursor used with different sort/filter params, or malformed → `422 VALIDATION_FAILURE`.
- Common filters where the resource has the column: `brand_id`, `campaign_id`, `status` (repeatable), `platform` (repeatable), `created_after`, `created_before`, `include_archived` (default `false`).

### 1.4 Errors — `ErrorResponse`
Every non-2xx response (including FastAPI/Pydantic validation errors, 404 for unknown routes, and 405) uses the glossary envelope:
```json
{ "code": "INVALID_STATE_TRANSITION", "message": "Content asset is REJECTED; APPROVE requires AWAITING_APPROVAL.",
  "correlation_id": "0192f7c2-...", "details": { "entity": "content_asset", "id": "...", "from": "REJECTED", "action": "APPROVE" } }
```
- `message` is user-safe; stack traces, SQL, secrets, and provider raw payloads are never included (they go to JSON logs keyed by `correlation_id`, §28).
- `details` for `VALIDATION_FAILURE` from request parsing: `{ "errors": [ { "loc": [...], "msg": "...", "type": "..." } ] }`.

HTTP ↔ `ErrorCode` mapping (one code may appear at several statuses only where listed):

| ErrorCode | HTTP | Typical source |
|---|---|---|
| `VALIDATION_FAILURE` | 400 (missing required header, e.g. `Idempotency-Key`), 413 (payload too large), 415 (content type), 422 (body/query invalid) | request parsing, upload checks; `details.reason` disambiguates |
| `VALIDATION_FAILURE` (`details.reason = NOT_IMPLEMENTED`) | 501 | route/format is in the v1 contract but not implemented in the current phase (e.g. `/content/{id}/repurpose` before Phase 10) |
| `UNAUTHORIZED` | 401 | missing/invalid token, bad login, bad webhook signature/timestamp |
| `FORBIDDEN` | 403 | role too low |
| `NOT_FOUND` | 404 | unknown id (also returned for archived rows unless `include_archived=true`) |
| `CONFLICT` | 409 | unique violation, stale `content_version_id`/`If-Match`, idempotency key reused with different body or still in progress |
| `INVALID_STATE_TRANSITION` | 409 | state-machine guard rejected an action |
| `PUBLICATION_UNCERTAIN` | 409 | manual retry/cancel of an `UNCERTAIN` job (must reconcile first). *Not* returned by SCHEDULE/PUBLISH_NOW: an open uncertain publication on the account holds jobs in `RETRY_WAIT` at dispatch (§6.5) |
| `LIVE_PUBLISH_BLOCKED` | 403 | A6 live-publish guard refusal (§6.5); `details.guard` names the failed condition |
| `SSRF_BLOCKED` | 422 | URL rejected by §26 guard (sync pre-check) or job failure code |
| `INGESTION_FAILURE` | 422 (sync) / job error | parser failure, corrupted file, `details.reason = NOT_IMPLEMENTED` for AUDIO/VIDEO/YOUTUBE_URL in MVP |
| `PRIVACY_VIOLATION` | 422 | override/routing would send `PRIVATE` task to a `REMOTE` model (§52) |
| `BUDGET_EXCEEDED` | 409 | campaign budget pre-flight check (§51) |
| `RATE_LIMITED` | 429 | API rate limiter (§6.4); includes `Retry-After` |
| `QUEUE_FAILURE` | 503 | cannot enqueue (Redis down); nothing was persisted as "queued" |
| `DATABASE_FAILURE` | 503 | DB unavailable |
| `MODEL_UNAVAILABLE`, `PROVIDER_RATE_LIMIT` | 503 | only on sync model calls (health probe); otherwise surface as job errors |
| `MODEL_TIMEOUT`, `PLATFORM_TIMEOUT` | 504 | same as above |
| `PLATFORM_AUTH_FAILURE`, `PLATFORM_RATE_LIMIT` | 502 / 503 | platform verify/reconcile calls (Phase 13+); job errors otherwise |
| `LLM_OUTPUT_INVALID`, `RESEARCH_FAILURE` | job error (502 if ever sync) | generation/research jobs; raw payload persisted in `model_runs` (AGENTS.md §4) |

Unhandled exceptions → `500` with `code = INTERNAL_ERROR` (GLOSSARY §4a); the exception is always logged with context and the correlation id (AGENTS.md §3: never swallowed). No stack trace in the body.

Every table row below implicitly also returns `401`, `403` (if min role > VIEWER), `422` (validation), `429`, `503`. The "Status" column lists success codes and **endpoint-specific** errors only.

### 1.5 Correlation ID — `X-Correlation-ID`
- Inbound: if present and matching `^[A-Za-z0-9._:-]{1,128}$`, it is adopted; otherwise (absent or invalid) a UUIDv7 is generated (an invalid inbound value is logged, never rejected).
- Outbound: echoed on **every** response (including errors and 202s) and copied into `ErrorResponse.correlation_id`.
- A separate `X-Request-ID` (always server-generated) is also returned (§28 `request_id`).
- Propagation: stored on `jobs`, `agent_runs`, `model_runs`, `publication_jobs`, `audit_events`, and passed into RQ job metadata so worker/scheduler logs share the id of the originating request.

### 1.6 Idempotency — `Idempotency-Key`
- Header value: 8–128 chars `[A-Za-z0-9_-]`. Retention 24 h.
- Stored in Postgres `idempotency_keys` (DATA_MODEL §6a.2), unique on `(principal_type, principal_id, method, route, key)` where `principal_type ∈ {USER, WEBHOOK_ENDPOINT}` and `route` is the route template. The row holds `sha256(canonical request body)` and the response status + body (NULL while in progress).
  - Same key + same body, completed → replay the stored response with header `Idempotent-Replayed: true` (no new side effects).
  - Same key + same body, in progress → `409 CONFLICT` (`details.reason = IDEMPOTENCY_IN_PROGRESS`).
  - Same key + different body → `409 CONFLICT` (`details.reason = IDEMPOTENCY_KEY_REUSED`).
- **Required** (missing → `400 VALIDATION_FAILURE`, `details.reason = IDEMPOTENCY_KEY_REQUIRED`) on every POST marked **[IK]** in the tables: all job-creating POSTs and all POSTs with external or publication effects (§37 `SCHEDULE`/`PUBLISH_NOW`, reconcile, mark-published, publication-job retry, analytics pull, source ingest, webhook deliveries use `X-OmniGrowth-Delivery-ID` instead). Optional on other POSTs.
- This is **request-level** idempotency. It complements, and never replaces, the A3 DB-level guarantee `publication_jobs.idempotency_key = sha256(content_version_id + platform_account_id)`, enforced by a **partial unique index** over `status IN (PENDING, CLAIMED, RETRY_WAIT, SUCCEEDED, UNCERTAIN)` (pending human approval, ADR-0003; STATE_MACHINES §3.1). A `SCHEDULE` of the same version to the same account with a *different* header key still yields `409 CONFLICT` while a job for that pair is in one of those states; `FAILED`/`CANCELLED` rows do not block, which is what makes manual retry (a new row) possible.

### 1.7 Long-running work — `202 Accepted` + `JobRead`
- Anything that calls a model, parses files, fetches URLs, pulls analytics, computes embeddings, or runs QA is queued (RQ, A3 / §30) and returns `202 Accepted` with a `JobRead` body (or an action-specific wrapper that embeds one) and `Location: /api/v1/jobs/{job_id}`.
- The API never blocks a worker thread on a model call, except `POST /models/health/probe` (bounded timeout, OWNER-only).
- Job status is polled via `GET /jobs/{id}`; `JobRead.result` holds **references** (ids of created rows), never large payloads. Failure → `JobRead.status = FAILED` with `error: { code: ErrorCode, message }`.
- Publications are **not** generic jobs: they are `publication_jobs` rows in the Postgres outbox (A3) claimed by the `scheduler`; `SCHEDULE`/`PUBLISH_NOW` return `PublicationJobRead`.
- Enqueue order: the `jobs` row is committed in the same DB transaction as any state change it implies; the RQ enqueue happens after commit. If enqueue fails the row is marked `FAILED` with `QUEUE_FAILURE` and the endpoint returns `503` (no silent "queued" row). A startup sweep re-enqueues `QUEUED` rows older than N minutes (Redis-loss recovery).

### 1.8 Other conventions
- **No hard deletes of domain rows** (GLOSSARY §1). Removal = `POST …/archive` (sets `archived_at`) and `POST …/restore`. `DELETE` is used only for: API tokens, platform credential secret material, webhook endpoints/subscriptions, derived-metric definition drafts — never content, publications, or audit.
- **State changes are action endpoints** (`POST …/pause`), never `PATCH { status }`. `status` is read-only in every `*Update` schema (AGENTS.md §4: only the state-machine module writes it). Every action records `actor_type` (`HUMAN` for API users, `SYSTEM` for webhook-triggered) + `actor_id`, and an `audit_events` row.
- **Optimistic concurrency:** `*Read` schemas carry `updated_at`; `PATCH` accepts optional `If-Match: "<updated_at ISO>"` → `409 CONFLICT` on mismatch. §37 actions *require* `content_version_id` in the body for the same purpose.
- `201 Created` responses include `Location`.

## 3. Schemas — names and key fields

Not full definitions; enough to reconcile with `docs/DATA_MODEL.md`. All `*Read` include `id`, `created_at`, `updated_at` unless noted; brand-scoped ones include `brand_id`. `*Update` = all fields optional (PATCH semantics), never `status`. Pydantic models use `extra="forbid"` on requests.

### 3.1 Common
- `Page[T]`: `items: list[T]`, `next_cursor: str | None`.
- `ErrorResponse`: `code: ErrorCode`, `message`, `correlation_id`, `details: dict | None`.
- `JobRead` (table `jobs`, DATA_MODEL §6a.1): `id`, `kind: JobKind`, `status: JobStatus`, `progress: int | None`, `brand_id`, `campaign_id`, `subject_type`, `subject_id`, `requested_by_type: ActorType`, `requested_by_id`, `correlation_id`, `queued_at`, `started_at`, `finished_at`, `attempt_count`, `result: dict | None` (refs, e.g. `source_asset_id`, `content_asset_ids`, `skipped`, `no_transition`), `error: {code: ErrorCode, message} | None`.
- `CancelRequest`: `reason: str | None`.
- `RegenerateRequest`: `instructions: str | None` (≤ 4 000 chars), `routing_override: ModelRole | None` (subject to privacy check).
- `HealthRead`: `status: HealthStatus` (`OK, DEGRADED, DOWN`), `checks: {database, redis, local_llm: HealthStatus}`, `time`.
- `HealthDetailsRead`: `HealthRead` + `versions`, per-check `latency_ms`, `queue_depth`, `outbox_lag_seconds`, `providers: list[ProviderHealth]`.

### 3.2 Auth / users
- `LoginRequest`: `email`, `password` (≤ 1 024 chars).
- `TokenRead`: `access_token`, `token_type="bearer"`, `expires_at`, `user: UserRead`.
- `ApiTokenCreate`: `name`, `expires_at` (≤ 90 d). `ApiTokenRead`: `id`, `name`, `prefix` (first 8 chars), `created_at`, `last_used_at`, `expires_at`, `revoked_at`. `ApiTokenCreatedRead`: `ApiTokenRead` + `token` (once).

## 6. Security

### 6.1 Endpoints that never return secrets
- `platform_credentials`: write-only via `PUT /platform-accounts/{id}/credentials` (`SecretStr` fields). No endpoint, log line, audit row, error `details`, job `result`, or OpenAPI example ever contains values; reads expose `PlatformCredentialStatusRead` only. A test asserts that a credential value written via the API does not appear in any response body, log record, or `audit_events.data`.
- Passwords (argon2id) and `api_tokens` hashes are never returned. Token plaintext only in `TokenRead` / `ApiTokenCreatedRead` at creation. Webhook secrets only in `*CreatedRead` at creation/rotation.
- `GET /health` (unauthenticated) exposes component states only. `/settings`, `/models`, `/health/details` never include API keys or credential-bearing URLs; model raw payloads (which may include private source text) only via OWNER + `include_payload=true`, masked by the logging secret filter.
- Log/secret masking filter (Phase 2 core) is applied to request logging; request bodies of `/auth/*`, `/platform-accounts/*/credentials`, `/webhooks/*` are never logged.

### 6.2 Upload and ingestion limits (all env-configurable; values are defaults)
| Input | Limit | Validation |
|---|---|---|
| Any JSON body | 1 MiB (`413`) | Pydantic `extra="forbid"`, string length caps, list length caps |
| `POST /sources/text` content | 1 MiB UTF-8 | valid UTF-8, NUL bytes rejected |
| `POST /sources/upload` document | 25 MiB (`OMNIGROWTH_MAX_UPLOAD_BYTES`) | streamed; aborted when exceeded (no full buffering); allowed: `text/plain`, `text/markdown`, `application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `application/x-subrip`, `text/vtt`; declared type, extension, and magic bytes must agree (`415`); PDF parsed with page/objects caps, DOCX zip-bomb guard (uncompressed ≤ 10× and ≤ 100 MiB), filename sanitized and never used as a path |
| Audio/video upload | 500 MiB (`OMNIGROWTH_MAX_MEDIA_UPLOAD_BYTES`) | stored only; processing `NOT_IMPLEMENTED` until transcription phase (§9 Q4) |
| `POST /sources/url` fetch | 10 MiB body, 10 s connect / 30 s total, ≤ 5 redirects | §26 guard: `http/https` only, ports 80/443, block loopback, RFC1918, link-local (incl. `169.254.169.254` metadata), CGNAT `100.64/10`, ULA `fc00::/7`, `::1`, IPv4-mapped IPv6, unspecified/multicast/reserved; resolve-then-connect to the pinned IP (DNS-rebinding defense); re-validate each redirect hop; allowed content types `text/html`, `text/plain`, `text/markdown`, `application/pdf` |
| Analytics batch | 500 snapshots | counts ≥ 0 except `followers_gained` (net); `publication_id` must belong to a caller-visible brand |
| Webhook body | 1 MiB | HMAC over raw bytes before JSON parsing |

### 6.3 Input validation
- Strict Pydantic v2 request models (`extra="forbid"`, `strict` numeric types, enum types from GLOSSARY, bounded strings/lists). Path IDs typed as UUID (malformed ⇒ 422, never a DB error).
- URLs in any body (`canonical_url`, `funnel_destination_url`, `target_url`) must be absolute `https` (or `http` for source ingestion only) and are **not fetched** except by the SSRF-guarded fetcher.
- Free-text fed to models is treated as data: prompts are templated from files (AGENTS.md §4), model output is schema-validated (§35), and no endpoint executes model output or shell strings (AGENTS.md §3).
- Formula strings in derived metric definitions are parsed into a whitelisted AST; no `eval`.

### 6.4 Rate limits (Redis-backed, sliding window; env-configurable)
| Bucket | Default | Key |
|---|---|---|
| Unauthenticated (`/health`, `/auth/login`) | 30 req/min | per IP |
| Login attempts | 5/min and 20/hour | per IP **and** per submitted email (both enforced); exponential backoff after failures |
| Authenticated general | 300 req/min | per token |
| Job-creating / [IK] POSTs | 20 req/min | per token |
| Uploads + URL ingest | 10 req/min | per token |
| Inbound webhooks | 60 req/min | per webhook endpoint + per IP |

- Responses carry `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`; `429 RATE_LIMITED` adds `Retry-After`.
- Redis unavailable: login and job-creating routes **fail closed** (`503 QUEUE_FAILURE`, since the queue is down anyway); read routes fail open with a logged warning (§9 Q12).
- Client IP is taken from the socket peer; `X-Forwarded-For` honored only from `OMNIGROWTH_TRUSTED_PROXIES`.

### 6.5 Live-publish guard (A6) surfaced in the API
Authoritative definition: STATE_MACHINES §3.3 (four conditions + `ENV=test` hard block). The API surfaces it as follows.

- **Request-time pre-check** (§37 `SCHEDULE`, `PUBLISH_NOW`, `/publications/jobs/{id}/retry`): conditions 1–3 and the hard block are evaluated; a refusal returns **`403 LIVE_PUBLISH_BLOCKED`** with `details.guard`.
- **Dispatch-start re-check:** the same conditions are re-evaluated inside the dispatch-start transaction (J4), before any network I/O. The job outcome there follows STATE_MACHINES §3.3 and is visible via `PublicationJobRead.status` / `last_error_code`.
- **Condition 4 is not checked at request time.** At dispatch, an open `PUBLICATION_UNCERTAIN` on the same account holds the job in `RETRY_WAIT` (`last_error_code=LIVE_PUBLISH_BLOCKED`, `details.guard=OPEN_UNCERTAIN`, attempt not counted, J7). This applies in `MOCK` mode too, so tests exercise it.

| STATE_MACHINES §3.3 | Condition | Request time (SCHEDULE / PUBLISH_NOW / retry) | Dispatch start |
|---|---|---|---|
| hard block | `ENV=test` ⇒ live dispatch impossible | 403 `LIVE_PUBLISH_BLOCKED`, `details.guard=ENV_TEST` (normally unreachable: settings refuse `PUBLISH_MODE=LIVE` under `ENV=test` at startup) | dispatcher independently re-checks `ENV` and refuses (`LIVE_PUBLISH_BLOCKED`) |
| 1 | `PUBLISH_MODE == LIVE` | false ⇒ not a live dispatch (mock/manual publisher); not an error | same |
| 2 | `platform_accounts.live_enabled = true` | false while mode is LIVE ⇒ 403 `LIVE_PUBLISH_BLOCKED`, `details.guard=ACCOUNT_NOT_LIVE_ENABLED` (never silently downgraded to mock) | re-checked; outcome per STATE_MACHINES §3.3 |
| 3 | job's `content_version_id` = asset's `approved_version_id` and the version is approved | false ⇒ 403 `LIVE_PUBLISH_BLOCKED`, `details.guard=VERSION_NOT_APPROVED` (a stale `content_version_id` in the body is caught earlier as 409 `CONFLICT`) | re-checked; outcome per STATE_MACHINES §3.3 |
| 4 | no `PUBLICATION_UNCERTAIN` publication on the account | **not checked** | job held in `RETRY_WAIT` (all modes, incl. `MOCK`) |

`live-enable` refusals use the same code: 403 `LIVE_PUBLISH_BLOCKED` with `details.guard ∈ {ENV_TEST, CONFIRMATION_MISMATCH, NO_CREDENTIALS, CAPABILITY_UNVERIFIED}`.

`PUBLISH_MODE` itself is never writable through the API.

### 6.6 Inbound webhook verification (A7)
- Headers: `X-OmniGrowth-Timestamp` (unix seconds), `X-OmniGrowth-Delivery-ID` (unique, ≤ 128 chars), `X-OmniGrowth-Signature: v1=<hex>` where `hex = HMAC_SHA256(secret, "{timestamp}.{raw_body}")`.
- Reject (`401 UNAUTHORIZED`, generic message) if: header missing, `|now − timestamp| > 300 s`, or signature mismatch under every active secret (constant-time `hmac.compare_digest`; current + previous secret during rotation grace).
- Replay: `delivery_id` stored 24 h per endpoint; duplicate ⇒ `200` with original `WebhookAcceptedRead` and `replayed=true`, no re-execution.
- Webhook-triggered actions are limited to `allowed_event_types` and can never approve, schedule, publish, or touch credentials/settings.

### 6.7 Transport & headers
- TLS terminated at the reverse proxy in any non-local deployment; API refuses to start with `ENV=production` and `OMNIGROWTH_CORS_ORIGINS=*`.
- Responses set `Cache-Control: no-store` on authenticated routes, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'` for JSON routes.
